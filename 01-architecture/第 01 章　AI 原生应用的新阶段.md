# 第 01 章　AI 原生应用的新阶段

早期，企业做 AI 应用，首先考虑的是怎么把大模型接入业务。应用向模型发送提示词，用检索增强生成（RAG）补充企业知识，用工作流（Workflow）串联应用程序接口（API），再把结果交给人处理。模型主要负责理解问题和生成内容，下一步做什么，仍由应用代码或人决定。

过去一年，企业开始把更完整的任务交给 Agent。以 Codex、Claude Code、Qoder 为代表的编程智能体（Coding Agent），不只给出代码建议，还能读取仓库、制定计划、修改文件、运行命令和测试，再根据结果继续调整。人可以在执行过程中补充要求、纠正方向，或者接手需要判断的步骤。

这些工作不是靠模型独自完成的。任务越长、工具越多，系统越需要记住进度、准备上下文、控制工具权限、隔离执行环境，并在失败后恢复、在交付前检查结果。本章用 Harness 统称模型之外的这套工程系统。后续章节会进一步说明其中各部分的分工。

本书用一个简单的公式说明二者的关系：Agent = Model + Harness。模型负责理解、推理、生成和决策，Harness 把这些能力组织成可以执行、检查和控制的工作过程。把 Agent 接入业务逻辑、数据、工具和用户交互，形成能完成业务任务的应用，本书称为 Agentic Application，以下也称 Agent 应用。它不只是一个回答能力更强的聊天机器人。

本章主要回答两个问题：Agent 应用与聊天、工作流、辅助工具有什么区别？企业应该怎样选择，才不会为了追求更高的自主性，把一个简单问题做复杂？

## 1.1 从生成内容到完成任务

### 1.1.1 上一阶段的 AI 原生应用

上一阶段的 AI 应用，通常围绕一次提问和一次回答展开。即使加入 RAG、函数调用（Function Calling）或多轮对话，单次任务的范围也比较明确，往往在几秒或几分钟内结束。

执行步骤主要由代码或工作流提前设定。模型可以分类、生成参数，或在少量工具中作出选择，但通常不负责从开始到结束持续决定下一步。

这类应用主要交付内容。人读一遍，就能初步判断回答是否通顺、有没有帮助。但如果要求系统修改代码、更新数据或完成一项操作，就不能只看最后的回答，还要检查工具调用、文件变更、数据库状态、测试结果等实际记录。

Chat/RAG 让人能用自然语言查询企业知识；Workflow 让模型参与既定的业务流程；Copilot 作为辅助工具，由人决定目标、下一步和最终结果。这些方式仍然有用。它们适合执行步骤比较明确，或者需要人持续作出专业判断的任务。

### 1.1.2 Coding Agent 为什么能说明这一变化

编程任务能清楚地说明：当 AI 从提供建议变成实际干活，系统需要补齐哪些能力。

首先，仓库里的代码通常放不进模型的一次上下文。Agent 需要搜索相关文件、筛选信息、保留摘要，并把暂时用不到的大量内容存到上下文之外。

其次，一项修改可能需要多次调用模型和工具。系统要保存计划、进度和待办，知道做过什么、还有什么没做。

工具会真的修改文件、运行命令或访问网络。系统必须限制权限、隔离环境，并让不可逆的操作先经过审批。

中间步骤也可能失败。系统需要记录错误，支持重试、检查点和任务恢复，而不是每次失败都从头再来。

最后，还要有人检查和引导。模型说“完成了”，不代表任务真的完成。代码需要按任务要求运行测试、构建和静态检查，还要审阅文件差异（Diff），必要时由独立评估器复核；人也不可能盯着每个生成的 Token，而应在目标、计划、高风险动作和最终验收这些关键位置参与。这种运行中的引导称为 Steering，让人参与关键判断的机制称为人在回路（Human-in-the-Loop）。

Anthropic 的长任务实践区分了会话（Session）、Harness 和沙箱（Sandbox），让模型循环可以持续改进，同时保持任务记录、执行工具和隔离边界稳定。OpenAI 的长任务实践则强调持久保存任务状态，支持中断后继续（Durable Thread），并使用可审阅的外部记忆、技能（Skills）、运行中的引导和人工复核。实现方式虽然不同，处理的是同一个问题：长任务不能只靠一段越来越长的对话，还要分别管理模型判断、任务状态、工具执行和安全控制。

### 1.1.3 编程之外，其他任务也需要这些能力

能读写文件、调用工具、保存进度并接受人引导的 Agent，也可以用于研究报告、数据分析、企业 IT 操作、客服工单和知识库维护。在风险较高的业务中，它还可以先准备操作方案和核验材料，交给人决定是否执行。

这些任务的业务内容不同，却经常需要同一批能力：接入模型、准备上下文、连接工具、保存任务状态和工作文件、控制权限、恢复失败任务、记录过程、评估结果和持续改进。如果每个应用都单独做一遍，会重复投入。把通用部分提取出来，就能形成可复用的 Harness 和共享的 Agent 平台（Agent Platform）。

| --- | --- |
| 生成一次回答 | 完成任务，并提供可以核验的结果 |
| 单轮或短会话 | 执行多个步骤，保存状态；必要时支持长任务和异步执行 |

## 1.2 从 Chat/RAG 到 Agentic Application：怎样选择应用形态

### 1.2.1 新的形态不一定要替代旧的形态

Chat/RAG、Workflow、Copilot、Single-Agent、Long-Horizon Agent 和 Multi-Agent 经常被排列成一条升级路线，好像越靠后就越先进。这容易误导选型。不同任务对执行步骤、自主程度、持续时间、分工和风险控制的要求不同，适合的方案也不同。

判断应用形态，不能只看它是不是聊天界面。更重要的是：谁决定下一步，哪些步骤提前写好，哪些步骤在执行时选择，系统能改变哪些外部数据或环境，以及任务是否需要跨会话继续，或者由多个 Agent 协作。

本书将 Agentic Application 分成三种形态。Single-Agent（单智能体）由一个 Agent 负责整个任务循环，在明确的范围内完成任务。Long-Horizon Agent（长程智能体）重点解决跨会话、跨进程持续执行的问题。Multi-Agent（多智能体）重点解决多个 Agent 如何分工和协作。后两种可以分别使用，也可以组合，但不是每个应用都必须经历的升级步骤。

### 1.2.2 Workflow 与 Agent 将长期共存

Workflow 的步骤明确，容易测试和审计。Agent 则适合步骤难以提前写全、需要根据现场结果继续判断的任务。企业流程通常两种情况都有。例如，资格校验、账务入账和交易审批更适合确定性流程；材料理解、异常调查、方案生成和动态选择工具，可以交给 Agent。

因此，本书建议把 Workflow 与 Agent 结合使用，这种方式称为混合形态（Hybrid）。可以让 Agent 负责工作流里的一个步骤，把它能做的事限制在明确范围内；也可以让 Agent 调用经过测试的工作流或 Skill，复用已经可靠的方法，不必每次都重新推理。低风险、能撤销的操作，可以给 Agent 更多自主权；高风险、不可逆的操作，要增加检查和人工审批。

Google 总结的 Agent 设计模式包括顺序、并行、协调器、层级分解、评审和改进，并讨论了延迟、成本、共享状态和错误传播之间的取舍。选择哪种模式，仍要回到任务本身：增加自主性、延长执行时间或引入更多 Agent，究竟解决了什么问题，新增的风险和工程成本是否值得承担。

### 1.2.3 什么时候需要长程智能体或多智能体

任务如果需要跨会话持续执行，就不能只把进度放在模型上下文里，也不能假设某个进程会一直运行。系统要保存持久状态、检查点和可审阅的外部记忆，并提供调度与恢复能力。这样，即使上下文被压缩、模型被更换、人暂停了任务或进程中断，也能从正确的位置继续。这是 Long-Horizon Agent 要解决的问题：不只是运行时间长，还要记得目标、进度、责任和结果。

任务如果涉及多个专业角色、工具权限或组织，把所有事情交给一个 Agent，可能导致上下文过大、职责冲突、权限过宽，也难以定位错误。Multi-Agent 可以通过顺序、并行、协调、交接或评审，让不同 Agent 在各自的角色和权限范围内协作。它的价值不是多调用几次模型，而是把分工、信息隔离和相互检查安排清楚。

二者解决的是不同问题：长程智能体处理任务如何持续，多智能体处理任务如何分工。一个 Agent 可以做长任务，多个 Agent 也可以只做短任务。在研究、研发、运维和复杂业务流程中，两种方式也可以组合。

这些扩展都会增加运行、隔离、观测、评估和治理的要求，还会增加延迟和成本，并带来状态同步、错误传播等风险。只有当简单方案不能以合理成本可靠完成任务，而新方案能解决这些限制时，才值得增加复杂度。

## 1.3 Agentic Application 是什么，不是什么

### 1.3.1 定义

本书所说的 Agentic Application，是把 Agent 用到具体业务中的完整应用：

> _它以 Model 与 Harness 组成的 Agent 为核心，再连接业务逻辑、数据、工具、运行环境和用户交互。用户给出业务目标后，系统准备上下文、保存任务状态，根据执行结果规划下一步、调用工具，并在明确的权限和控制范围内交付可核验的结果。_

可以用下面的公式帮助理解：

> _Agent = Model + Harness_

模型负责理解、推理、生成和决策。它不能独自完成上下文准备、进度保存、工具执行、权限控制、故障恢复和结果检查。Harness 负责把这些工作组织起来，让模型能够持续执行任务。

这里的 Harness 是广义用法，统称模型之外的工程系统，不是指一个包办所有事情的组件。实际实现时，要继续分清各部分的职责。

任务循环（Agent Loop）组织模型和工具的调用，根据执行结果继续下一步。上下文（Context）提供模型当前需要的信息，状态（State）保存任务进度，记忆（Memory）保留以后还可以复用的信息和经验。

工具（Tool）提供执行操作的接口。技能（Skill）把可复用的方法组织成说明或步骤，供 Agent 使用。协议（Protocol）约定系统之间怎样连接和交换信息。

运行时（Runtime）负责调度任务和处理执行中断，沙箱提供隔离的执行环境。可观测能力（Observability）记录执行过程，评估（Evaluation）检查效果。安全（Security）和治理（Governance）明确身份、权限和策略，并支持审批与审计。

业务应用负责定义任务和成功标准，通用组件提供执行与检查能力，不能代替业务验收。

不同产品可以采用不同的组件划分，但都需要说清：这些能力由谁提供，怎样配合，哪些限制必须由系统强制执行，不能让模型自己决定是否遵守。

### 1.3.2 判断一个应用的六个方面

判断一个应用是否属于 Agentic Application，可以看下面六个方面。

第一，是否围绕任务和结果工作。用户给出的不只是一个问题，还包括要完成什么、结果怎样才算合格。

第二，是否能在执行时调整步骤。系统根据中间结果、工具返回和环境变化决定下一步，而不是只执行提前写好的完整流程。

第三，是否能操作外部环境。Agent 可以调用 API、查询数据、修改文件、运行代码、操作浏览器，或者把任务交给另一个 Agent。

第四，是否能保存跨步骤、跨请求的任务状态。进度不只保存在当前模型上下文里。需要长时间执行的任务，还要能暂停、恢复、重试或交给另一个实例继续。

第五，是否有模型不能绕过的限制。系统要强制实施权限校验、沙箱隔离和预算限制，检查输出格式，并在需要时暂停等待审批或处理失败。中间件可以在模型和工具调用前后检查、拦截操作，不能只靠提示词提醒模型遵守规则。

第六，是否能通过记录和评估改进。系统需要记录执行过程、工具调用、状态变化、资源消耗和人工反馈。根据这些记录改出的新版本，还要经过回归测试、灰度验证和审批，才能进入生产。

这六项用于帮助判断，不是每个应用必须同时开启的功能清单。也不是自主权越大就越好，更不要求默认采用长程智能体或多智能体。重点是能在可控范围内，把业务目标变成实际工作，并检查结果。

### 1.3.3 几个容易混淆的概念

表 1-3 列出了本书使用的主要概念。区分它们，是为了避免把模型、框架、业务应用和共享平台当成同一件事。

| 概念 | 在本书中的含义 | 不等同于 |
| --- | --- | --- |
| Model | 提供语言理解、推理、多模态、生成和工具选择能力的模型 | 完整 Agent 或完整应用 |
| Agent | Model 与 Harness 共同组成，围绕目标观察、判断、行动，并根据反馈继续工作；Agent 与业务逻辑等结合形成的完整应用，称为 Agentic Application | 任意用了模型的软件，或一次模型调用 |
| Harness | 模型之外，组织和控制任务执行的工程系统；实际实现时要拆分上下文、状态、工具、运行、隔离、观测、评估和治理等职责 | 一条提示词、一个简单循环，或某个具体框架 |
| Single-Agent | 一个 Agent 负责任务循环，在明确范围内完成任务 | 需要跨会话持续执行的单 Agent 应用（属于 Long-Horizon Agent），或只有对话、没有工具与状态能力的应用 |
| Long-Horizon Agent | 能跨会话或进程继续任务，通过持久状态、检查点、恢复和人工引导保持进度 | 仅仅扩大上下文，或让一次模型调用持续更久 |
| Multi-Agent | 多个 Agent 按角色、能力或权限分工，通过编排、通信、交接或评审共同完成任务 | 简单并发调用多个模型，或把任务拆成多个提示词 |
| Agentic Application | Agent 与业务逻辑、数据、工具、环境和用户交互结合的完整应用；包含单智能体、长程智能体和多智能体三种形态 | 一次模型调用、SDK、框架或共享平台 |
| Agent Platform | 为多个 Agent 应用提供共享的设计、构建、运行、治理和调优能力的平台 | 某个业务 Agent 或单个业务应用 |

其中，三个区别尤其重要。

Agent 不等于 Agent 框架。框架可以提供任务循环、工具接入和记忆等开发能力，但企业仍要接入业务和运行环境，做好上下文、状态、权限、运行保障和结果检查，才能形成可用的应用。

长程智能体和多智能体不代表更聪明，也不代表更成熟。长任务会增加进度偏离、恢复和成本控制的难度；多个 Agent 会增加通信、共享状态、错误传播和责任划分的问题。先验证单 Agent 能做到哪里，再判断是否确实受时间、上下文、职责、权限或并行效率限制，不要仅为使用这些名称而升级。

应用形态也不等于平台能力。单智能体、长程智能体和多智能体描述任务怎样执行；平台描述多个应用共用哪些能力。同一种应用可以独立运行，也可以依托平台。平台更完善，不代表每个应用都要改成长程或多智能体。

## 1.4 从能演示到能稳定运行：怎样判断成熟度

### 1.4.1 不要只看产品名称

产品名里有 Agent，不代表它能稳定完成任务。一个以 Workflow 为核心的系统，也可能已经把状态保存、权限控制、过程记录和结果评估做得很好。判断成熟度，要看谁决定下一步、任务能持续多久、会影响哪些外部系统，以及运行和治理能力是否够用。

本书用四个级别帮助判断单个应用的能力和不足。这是本书采用的分析方法，不是对企业战略、组织、流程和文化的整体评级。

| 成熟度 | 典型应用与运行状态 | 核心能力 | 典型局限 | 需要补齐的能力 |
| --- | --- | --- | --- | --- |
| L1 辅助生成 | Chat、RAG、基础 Copilot | 生成内容、检索知识、调用简单工具 | 人负责完成和验收整个任务，系统很少保存执行状态 | 复用提示词和知识，建立基础评测 |
| L2 受控自动化 | Workflow，或在其中局部使用 Agent | 固定流程、结构化输出、局部动态选择、审批 | 不容易处理未知路径和复杂异常 | 明确自主范围，补齐 Harness、工具策略和过程评估 |
| L3 Agentic Execution（由 Agent 持续执行任务） | 单智能体、长程智能体、多智能体或 Hybrid | 动态规划、操作工具和环境、执行多步骤任务、保存状态、故障恢复 | 成本、权限、错误传播和版本变化可能影响可靠性 | 建立运行时、沙箱、可观测、安全和评估能力 |
| L4 规模运营与持续优化 | 多个任务或租户稳定运行，有统一治理和持续改进 | 共享资源、策略控制、过程记录、安全、离线与在线评估、灰度验证 | 系统更复杂，需要平台能力和组织管理配合 | 用共享平台、组织知识、标准和自动化降低管理成本 |

表 1-4　Agentic Application 应用成熟度参考模型

L4 是运行、治理和持续改进的能力水平，不是一种新的应用形态。企业通常要同时补齐应用、共享平台和组织管理能力。单智能体、长程智能体、多智能体都可以处于 L3 或 L4：形态取决于任务怎么组织，成熟度取决于系统能否可靠地运行和管理。

这四个级别也不是每个应用必须依次通过的关卡。低风险的知识助手可以长期采用 L1；交易审批可以保留 L2，以确定性工作流控制核心步骤；研发、运维、研究和复杂客服等任务，如果路径难以提前安排，可以采用 L3。当应用要同时服务大量任务、用户或租户，或者涉及共享资源、企业数据和高影响操作时，就要补齐 L4 所要求的能力。

选型时，先用能满足需求、成本和风险都能接受的简单方案。这就是本书所说的“最低充分架构”。成熟度模型用来发现缺了什么，不是催着应用升级。只有当前方案无法可靠完成任务，而新增能力有明确价值时，才需要调整架构。

### 1.4.2 构建之前，先把几个问题想清楚

把 AI 应用从演示带到生产，应该先确定架构，再选择具体工具。不是组件越多越好，而是要先明确目标、风险、执行时间、协作范围和运行规模，再决定哪些工作交给模型，哪些由确定性流程处理，哪些必须由人判断。

架构设计首先回答：用 Workflow、Single-Agent 还是 Hybrid？是否真的需要长程执行或多个 Agent？任务到哪里结束，Agent 有多大自主权，人与 Agent 怎样分工，哪些位置必须检查和审批？

构建要回答：怎样组合模型、任务循环、上下文、状态、记忆、工具、技能和协议？哪些步骤允许动态选择，哪些应写成固定流程、规则或可复用 Skill？

运行要回答：任务怎样排队和调度，状态怎样保存，工具在哪里执行，失败后从哪里恢复，任务和租户之间怎样隔离？

治理要回答：谁对 Agent 负责，它能以什么身份访问哪些资源，哪些操作必须审批，怎样记录、审计和处理异常？

调优要回答：怎样检查结果质量，从执行轨迹（Trace）和反馈里找到问题，调整模型、提示词、上下文、技能或 Harness？改完后，怎样通过回归测试、仿真和灰度验证效果，不合格时怎样回滚？

这些问题不是只在项目开始时问一遍。架构先明确分工和限制，构建、运行、治理、调优在后续使用中反复进行。下一章会给出参考架构，说明这些能力怎样组合。

### 1.4.3 多个 Agent 一起运行，谁来统一管理

一个 Agent 可以由应用团队自己管理。但多个 Agent 应用长期共用机器、数据和工具时，如果每个应用都各做一套调度、隔离、授权、恢复和审计，既重复投入，也难以检查它们是否遵守同样的规则。

操作系统一直在处理类似问题：多个程序共享硬件，需要安排执行、隔离进程、管理资源和权限。Agent 系统同样需要这些保障，不过还要管理跨会话的业务任务、运行时选择的工具，以及已经产生的外部操作结果。

这里不是说传统软件没有持久状态、动态权限或任务恢复。数据库和业务系统早就在处理这些问题。表 1-5 比较的是操作系统直接管理的进程和资源，与 Agent 系统还需要管理的任务和操作。

| 管理维度 | 操作系统通常直接管理的对象 | Agent 系统还需要管理的对象 |
| --- | --- | --- |
| 执行单元 | 进程或线程 | 任务运行实例（Run），一项任务可能跨进程、会话或副本继续 |
| 状态 | 进程内存、文件等资源 | 独立于执行实例保存的任务状态和进度 |
| 能力接口 | 系统调用与设备访问 | 执行过程中按需接入和选择的工具与 MCP 服务；MCP 即模型上下文协议（Model Context Protocol） |
| 授权 | 用户、进程和资源的访问权限 | 当前身份是否获准执行这次操作；高影响操作还需按策略检查，权限可撤销 |
| 故障恢复 | 进程重启、资源回收等机制 | 从正确步骤继续任务，避免重复操作，必要时撤销或补偿外部变更 |
| 审计 | 系统调用和文件访问等记录 | 用户目标、工具调用、环境反馈和结果之间的关联记录 |

表 1-5　从管理进程和资源，到管理 Agent 任务和操作

其中两件事需要特别注意。第一，启动时有权限，不代表之后每次操作都被允许。高影响动作要在执行前按策略检查，且检查必须放在模型不能绕过的位置。第二，进程重启不代表任务已正确恢复。任务可能正在等审批，也可能已经更新了外部系统。恢复前要确认实际进度，不能不加判断地把操作再做一遍。

这也解释了为什么要分清 Harness 和共享运行平台的职责。这里的 Harness 指构建与编排部分，不再泛指模型之外的全部工程系统。业务应用定义任务和成功标准；Harness 据此准备上下文、组织模型和工具调用，决定何时停止或请人介入。共享平台提供通用的调度、沙箱创建与回收、工作区和记忆的持久保存、预算控制及审计。业务授权和发布决定由负责治理的人或系统作出，共享平台按这些决定执行权限和策略检查。

共享平台不决定业务任务具体怎么做，也不定义业务成功标准。多个 Agent 都会用到的运行保障，则需要统一提供。例如，子任务能继承哪些权限和预算，怎样一次性撤销；哪个位置拦截高风险操作；恢复时怎样取回工作区快照。这些规则尤其不能只靠被检查的 Agent 自己遵守。

第 30 章用 Agentic OS 讨论这部分共同能力。这里先给出本书的判断：规模化运行多个 Agent 和长任务，需要共享的运行与治理机制。缺少这部分能力，各个应用就会重复实现调度、隔离、授权和审计。Agentic OS 不是一个已经确定的产品定义；怎样在现有云和运行平台之上实现这些机制，以及具体应当包括哪些能力，还需要继续讨论。

云平台和 Kubernetes 已经提供容器调度、资源配额和身份访问管理（IAM）等基础能力。但重启容器，不等于恢复一个已经改过外部数据的任务；容器健康，也不等于业务任务正确完成。Agent 系统仍需把这些基础能力与任务进度、操作授权、预算分配和实际记录连接起来。已有基础设施是支撑，不必重做；任务层的管理也不能因此省略。

这里先明确分工：架构和构建决定任务怎样执行；运行、治理和调优还需要共享的管理能力。第 02 章先说明完整参考架构，第 30 章再讨论 Agentic OS 的范围，以及哪些问题还没有确定答案。

## 1.5 本章小结

AI 应用正在从生成回答，转向由 Agent 实际执行任务。Coding Agent 已经说明：读取代码、修改文件、运行测试只是工作的一部分，还需要保存进度、控制权限、从失败中恢复，并检查结果。这些能力也适用于研究、运维、数据分析等任务。

Agent = Model + Harness 强调模型与工程系统缺一不可。本章用广义 Harness 统称模型之外的能力，下一章会继续分清具体组件和责任。Agentic Application 则把 Agent 接入完整业务，交付可以核验的结果。

选择应用形态时，先判断任务需要什么。单智能体负责明确范围内的任务；长程智能体让任务跨会话持续；多智能体让任务按角色分工。后两种可以分别使用，也可以组合，但都不是必经的升级步骤。Workflow 也不会因为 Agent 出现就失去价值，固定流程和动态判断可以一起使用。

选择复杂度时，先采用够用的简单方案。应用形态与成熟度要分开判断：一个 Agent 还是多个 Agent，取决于任务组织；能否稳定运行、统一管理和持续改进，取决于工程与治理能力。新方案必须能解决实际限制，收益也要足以覆盖新增成本和风险。

当多个 Agent 长期共用资源，调度、隔离、授权、恢复和审计就不宜再由每个应用重复实现。后续的 Agentic OS 一章会讨论，怎样在现有基础设施之上统一提供这些能力，同时保留业务应用、Harness 与共享平台各自的分工。
